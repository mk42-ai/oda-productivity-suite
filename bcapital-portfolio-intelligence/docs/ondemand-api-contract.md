## 2. Base URL, auth, content type

- Base URL: `https://api.on-demand.io` (`servers[0].url` in all four specs).
- Auth: security scheme named `apikey` — `type: apiKey, in: header, name: apikey`. Every operation declares
  `security: [{ apikey: [] }]`. Send the header `apikey: <YOUR_API_KEY>`.
- Request bodies are `Content-Type: application/json`; all responses are `application/json`.
- Success envelope: `{ message: string, data: <object | array>, pagination?: {...} }`.
- Error envelope (4XX `ClientErrorResponse`, 5XX `ServerErrorResponse`): `{ errorCode: string, message: string }`.

## 3. Chat / Agent Tools endpoints

### 3.1 Create Chat Session — `POST /chat/v1/sessions`

Params: none. Request body (`application/json`):

| Property | Type | Required | Description (from spec) |
| --- | --- | --- | --- |
| `externalUserId` | string | **yes** | An identifier of the external user creating this chat session. This user is external to OnDemand but internal to your own system which can be used for filtering sessions and auditing. If not managing chat users internally, use any unique string. |
| `pluginIds` | string[] (`maxItems: 20`) | no | A list of plugin IDs to be used in the chat session. A maximum of 20 plugins are allowed. This list can be empty. If set here and not overwritten through `/query` endpoint, then these plugins will be used for all queries in this session. |

200 `{ message: "Chat session created successfully", data: ChatSession }` where `ChatSession` =

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | ID of chat session |
| `companyId` | string | ID of the company linked to chat session |
| `externalUserId` | string | ID of the external user |
| `pluginIds` | string[] | List of plugins associated with the chat session |
| `title` | string | Auto-generated by OnDemand when the first query is submitted; empty until then |
| `createdBy` | string | ID of the company user created the chat session |
| `createdAt` / `updatedAt` | string (RFC 3339) | Timestamps |

4XX / 5XX: `{ errorCode, message }`.

### 3.2 Submit Query — `POST /chat/v1/sessions/{sessionId}/query`

| Param | In | Required | Type | Description |
| --- | --- | --- | --- | --- |
| `sessionId` | path | **yes** | string | ID of the session linked to this query |

Request body (`application/json`) — required: `query`, `endpointId`, `responseMode`:

| Property | Type | Required | Description (from spec) |
| --- | --- | --- | --- |
| `query` | string | **yes** | Actual query |
| `endpointId` | string | **yes** | Endpoint ID of the fulfillment model selected to fulfil the query. Can be a predefined, BYOI or BYOM model endpoint (example `predefined-openai-gpt4o`). |
| `responseMode` | string, enum `sync` \| `stream` \| `webhook` | **yes** | Response mode to get the query answer |
| `pluginIds` | string[] (`maxItems: 20`) | no | Plugin IDs made accessible to RAG to answer the query. Max 20. If specified, replaces the plugin IDs set during session creation. If not specified or empty, the session's plugin IDs are used. If not specified at any level, the system bypasses RAG and goes directly to fulfillment. |
| `fulfillmentOnly` | boolean, default `false` | no | If true, skips the RAG and only executes the fulfillment even if `pluginIds` is set at any level. Skipping RAG also skips plugin execution, so RAG-dependent queries will not be answered correctly. |
| `modelConfigs` | object | no | Fulfillment model configuration; defaults are used if omitted. |
| `modelConfigs.fulfillmentPrompt` | string | no | Prompt providing instructions that guide the model's approach to fulfilling the user's query. |
| `modelConfigs.stopSequences` | string[] | no | Up to 4 sequences where the API will stop generating further tokens. |
| `modelConfigs.temperature` | number (float), min 0, max 2, default 0.7 | no | Sampling temperature; alter this or `topP` but not both. |
| `modelConfigs.topP` | number (float), min 0, max 1, default 1 | no | Nucleus sampling probability mass. |
| `modelConfigs.presencePenalty` | number (float), min 0, max 2, default 0 | no | Penalises tokens already present in the text. |
| `modelConfigs.frequencyPenalty` | number (float), min 0, max 2, default 0 | no | Penalises tokens by existing frequency. |

200 ("Sync Mode Response") `{ message: "Chat query submitted successfully", data: {...} }`:

| `data` field | Type | Description |
| --- | --- | --- |
| `sessionId` | string | ID of chat session |
| `messageId` | string | ID of the chat message |
| `answer` | string | Answer to the query |
| `status` | string, enum `processing` \| `completed` \| `failed` | Current status of the chat message |
| `metrics` | object `{ inputTokens, outputTokens, totalTokens, ragTimeSec, fulfillmentTimeSec, totalTimeSec }` | **not documented (observed)** in the live probe response (probe-query.json) |

4XX / 5XX: `{ errorCode, message }`. Chat-specific codes: see §7.

## 4. Chat Batches — not a documented API

As of the 2026-10-13 fetch, the public documentation index (`/config/v1/public/docs/categories`, `llms.txt`)
contains **no Chat Batches category and no batch operation**. Live probes made this turn (all with the `apikey`
header; values quoted verbatim):

| Probe | Result |
| --- | --- |
| `GET https://api.on-demand.io/chat/v1/batches?limit=1` | 200 `{"message":"Chat batches fetched successfully","data":[],"pagination":{"next":"","limit":1}}` |
| `POST https://api.on-demand.io/chat/v1/batches` body `{}` | 405 `{"message":"Chat batch creation is currently unavailable","errorCode":"method_not_allowed"}` |
| `GET /chat/v1/batch`, `GET /chat/v1/batches/queries`, `GET /chat/v1/batches/status` | 404 `not_found` |

Conclusion: a list route exists but creation is disabled server-side and nothing is documented — **not documented
(observed)**. We do not depend on it.

Terminal states we CAN rely on (documented single-query API):

- `message.status ∈ { processing, completed, failed }` (spec enum, both on the `/query` 200 body and on `ChatMessage`).
- `completed` = terminal success (answer is final). `failed` = terminal failure. `processing` = non-terminal.
- `isBackgroundProcessing` (boolean, **not documented (observed)** — `false` on the completed probe message) indicates
  the server is still working on the message; treat `true` as equivalent to `processing`.

How this project runs a "batch": a **client-side bounded-concurrency set of documented single queries**.

1. Generate a local batch id (e.g. `pb-<ISO timestamp>-<random>`); it never goes to OnDemand.
2. Create one session per batch (`POST /chat/v1/sessions`, `externalUserId` such as `bcap-pitchbook-batch`,
   `pluginIds: ["plugin-1777018662"]`).
3. For each item submit `POST /chat/v1/sessions/{sessionId}/query` with `responseMode: "sync"`, running at most
   4 queries concurrently (§6).
4. If the sync 200 body already says `status: "completed"` or `"failed"`, the item is terminal — no further calls.
   Only when it says `"processing"` do we poll `GET /chat/v1/sessions/{sessionId}/messages/{messageId}` (fallback:
   `GET …/messages?limit=50&sort=desc` and match `id`) until the status is terminal or the per-item deadline expires.
5. Batch status = aggregate of item statuses; metrics come from `data.metrics` / `publicMetrics` when present.

## 5. Pagination

- Offset (`page`, `limit`): `page` starts at 1; `limit` default 10, max 50 unless stated otherwise. Documented for
  Fetch Media (`GET /media/v1/public/file?page=1&limit=10`). Not used by the Chat endpoints in this contract.
- Cursor (`cursor`, `limit`): used by Get Chat Sessions and Get Chat Messages. First call omits `cursor`; each
  response has `pagination: { next: string, limit: integer }`; `next` is `""` when no more results, otherwise pass
  it as `cursor` on the next call. On `getchatmessages` `limit` is int32, min 1, max 50, default 10.

## 6. Rate limits and our backoff policy

Documented: all endpoints are rate-limited per origin IP at **10,000 requests per minute** (reference/rate-limits).
Per-object limits on the free plan (docs/rate-limiting): **RAG Calls Per Minute – 100**, **Media Upload Per
Minute – 5**, Max GPU memory per company 40 GB, Max vCPU per company 10. Exceeding a limit returns 429
`rate_limit_exceeded`. Increases are requested via Settings → Limit → Increase Your Limits.

Policy used by this project (client-side, not a server guarantee):

- Concurrency **4** in-flight queries per batch; **250 ms** minimum spacing between query submissions
  (≤ 240 submissions/min, well under the 100 RAG calls/min only because each sync call takes tens of seconds; the
  spacing + concurrency cap together keep the practical rate under the limit).
- On HTTP **429** or **5xx** (and on `plugin_execution_timeout` 504): exponential retry with waits of **2 s, 8 s,
  30 s**, i.e. up to **3 retry attempts** (4 tries total), then mark the item `failed` with the last `errorCode`.
- 4xx other than 429 are not retried.

## 7. Error codes (from reference/errors)

Error body: `{ "errorCode": "<machine-parsable>", "message": "<human-readable>" }`,
e.g. `{"message":"Input params are missing or invalid","errorCode":"invalid_request"}`.

| HTTP | Code | Description |
| --- | --- | --- |
| 400 | `invalid_request` | The payload or parameters are invalid. |
| 401 | `unauthenticated` | Request was made with an invalid or unknown token. |
| 403 | `unauthorized` | The user does not have the necessary permissions to perform this action. |
| 404 | `not_found` | The requested resource or route was not found. |
| 405 | `method_not_allowed` | The requested method is not allowed. |
| 429 | `rate_limit_exceeded` | The user has sent too many requests in a given period. |
| 500 | `server_error` | An internal server error occurred. |
| 502 | `bad_gateway` | The server, acting as a gateway, received an invalid response while trying to fulfill the request. |
| 503 | `resource_unavailable` | The requested resource or service is currently unavailable. |

Chat API specific:

| HTTP | Code | Description |
| --- | --- | --- |
| 504 | `plugin_execution_timeout` | Any plugin execution timed out. Plugin execution timeout is 2.5 minutes. |
| 400 | `context_length_exceeded` | Maximum context length for the LLM model exceeded. |
| 500 | `model_error` | Unknown/unclassified LLM errors (network errors or timeouts during model calls, etc.). |

## 8. curl examples (replace `<YOUR_API_KEY>`; never commit a real key)

Create session:

```bash
curl -sS -X POST 'https://api.on-demand.io/chat/v1/sessions' \
  -H 'apikey: <YOUR_API_KEY>' -H 'Content-Type: application/json' \
  -d '{"externalUserId":"bcap-pitchbook-batch","pluginIds":["plugin-1777018662"]}'
# -> {"message":"Chat session created successfully","data":{"id":"<SESSION_ID>", ...}}
```

Submit query (sync):

```bash
curl -sS -X POST 'https://api.on-demand.io/chat/v1/sessions/<SESSION_ID>/query' \
  -H 'apikey: <YOUR_API_KEY>' -H 'Content-Type: application/json' \
  -d '{
    "query": "Call the getCompanyProfile tool with pbId=466799-77 and return the complete tool JSON response verbatim as your answer (no commentary).",
    "endpointId": "predefined-gpt-6-luna",
    "responseMode": "sync",
    "pluginIds": ["plugin-1777018662"],
    "modelConfigs": {"temperature": 0}
  }'
# -> {"message":"Chat query submitted successfully","data":{"sessionId":"...","messageId":"<MESSAGE_ID>","answer":"...","status":"completed","metrics":{...}}}
```

Get message (poll only while status is `processing`):

```bash
curl -sS 'https://api.on-demand.io/chat/v1/sessions/<SESSION_ID>/messages/<MESSAGE_ID>' \
  -H 'apikey: <YOUR_API_KEY>'
# fallback (documented list form, cursor pagination):
curl -sS 'https://api.on-demand.io/chat/v1/sessions/<SESSION_ID>/messages?limit=50&sort=desc' \
  -H 'apikey: <YOUR_API_KEY>'
```
